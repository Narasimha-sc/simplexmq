# Agent: choose another proxy when the chosen proxy keeps failing to forward

Stacked on "agent: choose another proxy when connecting to the chosen proxy fails" (`plans/2026-10-15-proxy-repick-on-connect-failure.md`), which handles a proxy that cannot be connected to.

## Problem

With private routing, a connection can stay at "connecting…", or a join can fail on every "Retry", until the app restarts. The sending agent chooses one proxy for each destination relay and keeps it. If that proxy cannot forward to the relay, every retry goes through the same proxy. After a restart of the app a proxy is chosen again, and the connection then completes in seconds.

Seen on 2026-10-14 with public servers: smp4 → smp10 forwarding timed out repeatedly for ~10 minutes, and connections for which smp4 had been chosen as the proxy for smp10 stalled for the whole time, in all app and CLI versions tried (simplex-chat 7.0.0.9, 7.1.0.10).

## Cause

`smpProxiedRelays` in `Agent/Client.hs` maps the destination session to the chosen proxy. A forwarded command (PFWD) fails with `PROXY (BROKER e)` other than a host error, e.g. `PROXY (BROKER TIMEOUT)`, when the proxy has a session to the relay but cannot reach it, or receives an invalid response from it. `sendViaProxy` only handles `PROXY NO_SESSION`; the proxy connection stays up, so the choice stays until the connection is closed.

The existing delayed resets do not replace such a proxy:
- The client's connection monitor drops a connection after 3 timed-out commands in a row and at least 15 minutes since the last received data. A proxy that answers PFWD with errors keeps the connection receiving data, so the monitor never drops it.
- The proxy's own connection to the relay is dropped by the same monitor on the proxy, which also deletes its sessions to that relay. The client then receives `PROXY NO_SESSION` in response to its next PFWD and, by design (#1178), creates a new session through the same proxy, and the proxy connects to the relay again. The proxy is changed only if that PRXY fails (e.g. the proxy cannot reconnect; it then keeps the connect error for 30 s). If the proxy reconnects but forwarding keeps failing, the stall continues.

## Fix

Delete the choice of the proxy for this destination when the proxy keeps failing, so that a proxy is chosen again on the next attempt.

After a `ProxyProtocolError (PROXY (BROKER e))` where `e` is not a host error, the start of the current streak of failures is recorded, if none is recorded. After a successful forwarded command the streak is cleared, because the proxy has reached the relay. On a failure at least `proxyFailureInterval` (new `AgentConfig` field, 30 s) after the start of the streak, the choice is deleted. The proxy has already received the destination, and a new one would too, so one timeout, or a burst of failures within 30 s (e.g. all requests in flight when the relay restarts), does not change the proxy chosen for the destination as long as a later forward reaches the relay.

The streak start is stored in `smpProxiedRelays` with the chosen proxy (`ProxyChoice`), so it is deleted together with the choice. Failures, successes and deletes change the entry only if it still contains that proxy (`lookupProxyChoice`, `isChosenProxy`; the deletes in `smpClientDisconnected` and `newProxiedRelay` also check it). After a failure at the interval the choice is deleted, but the proxy keeps its session to the relay, and a request that started a PRXY through it before may still be waiting. After another proxy is chosen, the later disconnect, failed PRXY, failure or success of the first proxy must not change the new choice.

Other PFWD errors neither start nor clear the streak, e.g. unexpected or unparsable responses from the proxy itself, `PROXY (PROTOCOL _)` (the relay's error to the proxy's forwarding request, which the proxy reports without proof from the relay), a response of the destination relay, returned through the proxy, of the wrong type or one that cannot be parsed, and a timeout in the client. (The relay's unexpected or undecodable responses to the proxy's forwarding request arrive as `PROXY (BROKER UNEXPECTED)` or `PROXY (BROKER RESPONSE)` and count; a response the proxy cannot decrypt arrives as `CRYPTO` and does not.) An error of the destination relay returned through the proxy (e.g. `AUTH`, `QUOTA`) clears the streak, like a success: it is encrypted for the client, so it proves that the proxy reached the relay. A failed PRXY still deletes the choice at once, as before. The direct-connection fallback is unchanged: it still depends on `serverHostError` of the returned error.

The next choice follows the usual rules (another operator and host than the destination's, when possible). It is not restricted to proxies other than the failed one: with k eligible proxies the failed one is chosen again with probability 1/k (with the preset servers 1/6 for a SimpleX Chat relay, 1/11 for a Flux relay and 1/17 for a relay outside the user's servers, such as a contact's own relay; 1/2 with two proxies). The new choice has no streak, so two failures at least `proxyFailureInterval` apart delete it.

### Timing

With the default timeouts on a fast network (the client's waits are 1.5 times longer on a slow network, so there the proxy's first report can arrive on an earlier attempt; the outcome is the same): the proxy waits for the relay for 30 s (`forwardSMPTransmission` uses `NRMBackground`), while background delivery waits 60 s for PFWD, so the proxy's `PROXY (BROKER TIMEOUT)` arrives first. Retries start 2 s apart, so the second report arrives about 32 s after the first, the choice is deleted, and a proxy is chosen again on the next retry, about a minute after the first send.

An interactive request such as joining a connection waits 20 s on the first attempt, then 30 s and 45 s on "Retry"; its client timeouts ("Connection timeout" in the app) do not count, and the first Retry's wait of 30 s ends before the proxy's report arrives, so the first proxy report ("Private routing timeout") arrives on the second Retry, the choice is deleted on the next Retry's report, and a proxy is chosen again on the Retry after it. With SOCKS or Tor the app's defaults are longer (40 s for the first interactive attempt), so the proxy's first report arrives on the first attempt.

Not changed: a host error reported by the proxy about the relay (PRXY or PFWD) keeps the entry, as before. E.g. an onion-only relay and a chosen proxy without Tor (`PROXY (BROKER HOST)`), or a relay whose protocol version the chosen proxy does not support (`TEVersion`), remain the choice for that relay; while direct sending is not allowed, such sends keep failing.

## Privacy

Each proxy used for a destination receives the client's IP address and the destination host, so a change of the proxy sends the destination address to one more proxy, as a failed PRXY already does. Over any number of changes the destination address reaches at most the eligible proxies, the same set as with restarts or failed PRXYs on master. Each change is a new choice: with downgrade allowed, when the connection to the newly chosen proxy fails with a host error, the message is sent directly, as after a failed PRXY on master (with the app default, only when the IP address is already protected).

The errors the client receives are the same for a proxy that cannot reach the relay and for a relay that responds incorrectly. A destination relay that does not answer the forwarded commands of a queue, answers the proxy's forwarding request with a response of the wrong type or one that cannot be decoded, or drops the proxy's connection during a forward makes the sender change the proxy for this relay (for this connection in the per-connection session mode), until a proxy whose operator colludes with the relay's operator is chosen. A change needs two such failures at least `proxyFailureInterval` apart. With unanswered forwards the failing message is retried at growing intervals; with wrong-type or undecodable responses each message fails at once without a retry, so every new send, including receipts triggered by a contact, is another failure, and changes can happen about once per `proxyFailureInterval` while the user sends. The number of changes is not limited.

A relay could already do this on master with failed PRXYs, which delete the choice at once and without limit: on receiving the forwarded command of a queue it closes the proxy's connection and rejects that proxy's reconnection, the next forward gets `NO_SESSION`, and the PRXY of the retry fails. That also changes the proxy for the other senders that use this proxy for this relay, so it takes several rounds to single out one sender. This change gives a relay a second method, which does not require rejecting any connection, and which can be applied to the forwards of one queue in a single round. A network attacker between the proxy and the relay can delay the traffic for more than the proxy's wait of 30 s, and so cause changes for all senders that use this proxy for this relay, as on master by cutting the connection and blocking the proxy's reconnection, so that the PRXY of the retry fails; this cannot be applied to one queue. A limit on the number of changes would bound only that second method, and would leave a proxy that stops forwarding chosen for a long time, so there is none.

The sends that fail can be sent by the user or triggered by a contact, e.g. delivery receipts for messages of a contact who hosts their queues on their own relay. A relay that leaves forwards unanswered can also make the client change the proxy for other relays reached through the same proxy connection, when many forwards are in flight at once (the proxy has 500 slots per client connection), on a slow network or with SOCKS, where the proxy's timeout is reported before the client's own.

The choice is shared by all queues of the user on the relay in every session mode except per connection, including the default. A change of the proxy after failures of one queue's forwards changes the proxy for all of these queues, so the operator of a relay that causes the change can identify the user's other queues on this relay by seeing which of them start receiving messages through the new proxy together. This includes incognito connections of the same profile and fetches of short links through this relay; a contact who hosts their queues on their own relay can link an incognito connection with them to the same profile's other connections in this way. A successful forward of another queue through the same proxy clears the streak, so the relay has to make the forwards to those queues fail as well. On master all of a user's queues on a relay already arrive through one proxy, which links them for a relay with few senders per proxy. Singling out one user on a busy relay is possible by disrupting every sender that uses a proxy, over several rounds, by an attacker on the client's network path who closes the client's connection to the proxy, or by watching changes of the proxy that happen anyway (a restart, a network change). This is the main cost of this change; avoiding it would need a separate choice for the failing connection, which is a larger change.

If the relay itself is unreachable for every proxy, that usually shows as failed PRXYs, which delete the choice on every retry, as before.

## Known limits

- A proxy that keeps its connection and answers neither a forwarded command nor with its own `PROXY (BROKER TIMEOUT)` (an unresponsive or overloaded server) is not replaced: the client's own timeouts are not counted, and the connection monitor drops a connection only if nothing at all was received on it for 15 minutes. A client timeout is also reported when the client's own network stops working (e.g. a switch between Wi-Fi and mobile data), and counting it would change the proxy for no reason.
- The start of a streak is not cleared by time or by an error of the destination relay: one isolated failure, with nothing succeeding afterwards, makes any later failure delete the choice. This is intended for a relay that keeps the proxy's connection but does not answer for hours, and gets rare sends, each of which fails. It also happens after failures of sends that are not retried (`UNEXPECTED`, `RESPONSE`, `TRANSPORT`, name lookups).
- A proxy that answers forwarded commands with errors that do not count, or with a host error, remains the choice; with a host error and downgrade allowed, the sends go directly, as on master. A new choice can be a proxy that reports a host error for the relay; no forward is sent through it, so no streak starts and the choice is not replaced, as with a failed PRXY on master.
- The relay stops reading a proxy's connection while forwarded name lookups wait for a free resolver slot (up to 30 s). Anyone using the same proxy can fill these slots with slow lookups and make every forward through this proxy to this relay end with `PROXY (BROKER TIMEOUT)`, which changes the proxy for all its senders to this relay, as a network attacker between the proxy and the relay can. It cannot be applied to one queue. A change in the server is out of scope here.
- If the destination relay itself is down or slow for every proxy, the streak changes the proxy without a benefit, and each change sends the client's address and the destination to one more proxy.
- A forwarded name lookup (RSLV) uses the same path as sending, and the same session key unless the session mode is per connection. The relay's resolver times out after 3 s by default and answers with a relay error, which does not count. A resolver slot wait plus the resolver time, or a resolver timeout of 30 s or more set by the operator, can exceed the proxy's 30 s wait and be reported as `PROXY (BROKER TIMEOUT)`, which counts.
- The proxy also reports `PROXY (BROKER TIMEOUT)` when it has no free slot among its 500 per-client slots for 60 s. On a fast network without SOCKS the background client's own timeout (60 s) expires first and is not counted; on a slow network (90 s) or with the app's SOCKS defaults (80 s) the proxy's report arrives first and counts. Slots are per client connection, so slow forwards to one relay can cause this report for another relay reached through the same proxy.
- The streak uses the wall clock: after a change of the clock backwards, no failure deletes the choice until the clock passes the start of the streak by the interval; after a change forwards by the interval or more, the next failure deletes it.
- When a `NO_SESSION` reply arrives after a failure at the interval deleted the choice, the invalid relay session is not removed, because it is found through the choice, and the retry through the same proxy uses it and records that proxy as the choice again, without a streak. The retry fails once, and the next change of the proxy needs two more failures at least `proxyFailureInterval` apart. After a failed PRXY or a disconnect the retry also records that proxy again, but sends a new PRXY. If another send has already chosen a new proxy, the retry goes through that proxy, and the invalid session stays in the old proxy until it is chosen again, when one more `NO_SESSION` removes it.

## Verification

Tests (`SMPProxyTests`; in the first two the bad proxy is set as the first choice and the agent's server RNG is seeded, so that the later choices are fixed):
- "chooses another proxy when the chosen proxy is offline" (from the previous PR, now taking a parameter that starts the bad proxy's server, or nothing).
- "chooses another proxy when the chosen proxy cannot forward to destination relay": the proxy's relay client uses a 1 µs command (response) timeout, so PRXY succeeds and every PFWD returns `PROXY (BROKER TIMEOUT)`, the error seen in production. The test uses `proxyFailureInterval` 0, so the second failure deletes the choice. Only SKEY passes through the bad proxy, and repeating it with the same key is accepted, so the repeated attempts are harmless. The bad proxy may be chosen again.
- After the connection completes in both, a successful send clears a streak that was set on the new choice.
- "keeps the chosen proxy until it fails for proxyFailureInterval": with explicit times, a failure within the interval keeps the choice and the start of the streak, the success or failure of another proxy changes nothing, a success clears the streak, and a failure at the interval after the start of the streak deletes the choice.

The guards in `smpClientDisconnected` and `newProxiedRelay`, and the wait-timeout exemption from the previous PR, are not covered by tests: they need a proxy connection that drops, or fails while another request waits for it.

Desktop and Android results are in the PRs.
